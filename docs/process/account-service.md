# account-service 프로세스

## 1. 서비스 역할

`account-service`는 사용자와 상품 정보를 관리하는 서비스입니다.

주요 역할은 다음과 같습니다.

- 사용자 정보 조회, 생성, 수정, 삭제
- 상품 정보 조회, 수정
- 주문/포인트 처리 결과를 받아 사용자 포인트 잔액 반영
- 자주 조회되는 사용자 상세 정보 캐싱

사용자가 직접 호출하는 API와, 다른 서비스가 내부적으로 호출하는 API가 함께 존재합니다.

## 2. 전체 흐름

```text
사용자/관리자
  -> account-service
     -> 사용자 정보 처리
     -> 상품 정보 처리
     -> Redis 캐시 조회/삭제
     -> PostgreSQL 저장

processing-service
  -> account-service Internal API
     -> 사용자 포인트 잔액 반영
```

`account-service`는 메시지 큐를 직접 소비하지 않습니다. 포인트 이벤트 처리는 `processing-service`가 담당하고, `account-service`는 최종 잔액을 전달받아 사용자 정보에 반영합니다.

## 3. 사용자 관리 프로세스

### 3.1 사용자 상세 조회

사용자 상세 조회는 Redis 캐시를 먼저 확인합니다.

```text
1. 사용자 상세 조회 요청
2. Redis에서 사용자 캐시 확인
3. 캐시가 있으면 바로 응답
4. 캐시가 없으면 DB에서 사용자 조회
5. 조회 결과를 Redis에 저장
6. 사용자 정보 응답
```

사용자 상세 캐시는 120초 동안 유지됩니다.

### 3.2 사용자 목록 조회

사용자 목록은 DB에서 조회합니다.

조회할 때 사용할 수 있는 조건은 다음과 같습니다.

| 조건 | 설명 |
| --- | --- |
| `status` | 사용자 상태로 필터링 |
| `name` | 이름 일부로 검색 |
| `sortBy` | 정렬 기준. 현재 `name`, 기본값 `createdAt` |
| `sortDirection` | `asc`이면 오름차순, 그 외에는 내림차순 |

### 3.3 사용자 생성

사용자 생성 흐름은 다음과 같습니다.

```text
1. 사용자 생성 요청
2. loginId 중복 확인
3. email 중복 확인
4. 중복이 없으면 ACTIVE 상태로 사용자 생성
5. 초기 포인트 잔액은 0으로 저장
6. 생성된 사용자 정보 응답
```

이미 사용 중인 `loginId` 또는 `email`이 있으면 생성하지 않습니다.

### 3.4 사용자 수정

사용자 수정 흐름은 다음과 같습니다.

```text
1. 사용자 수정 요청
2. 사용자 존재 여부 확인
3. email 중복 확인
4. 이름, 이메일, 전화번호 수정
5. DB 저장 완료 후 사용자 상세 캐시 삭제
6. 수정된 사용자 정보 응답
```

캐시 삭제는 DB 반영 이후에 수행됩니다. 그래서 다음 상세 조회부터는 최신 정보가 다시 캐시에 저장됩니다.

### 3.5 사용자 삭제

사용자는 실제로 DB에서 제거하지 않고 소프트 삭제합니다.

```text
1. 사용자 삭제 요청
2. 사용자 존재 여부 확인
3. 사용자 상태를 INACTIVE로 변경
4. deletedAt 저장
5. 사용자 상세 캐시 삭제
6. 성공 응답
```

이미 삭제된 사용자에 대해 다시 삭제 요청이 들어와도 캐시를 삭제하고 성공 처리합니다.

## 4. 상품 관리 프로세스

### 4.1 상품 상세 조회

상품 상세 조회는 DB에서 상품을 찾아 응답합니다.

상품이 없으면 `상품을 찾을 수 없습니다.` 오류를 반환합니다.

### 4.2 상품 수정

상품 수정 흐름은 다음과 같습니다.

```text
1. 상품 수정 요청
2. 상품 존재 여부 확인
3. productCode 중복 확인
4. 상품명, 상품코드, 가격, 재고, 상태 수정
5. 수정된 상품 정보 응답
```

이미 다른 상품에서 사용 중인 `productCode`는 사용할 수 없습니다.

## 5. 포인트 잔액 반영 프로세스

포인트 잔액 반영은 사용자가 직접 호출하는 기능이 아닙니다.

주문 또는 포인트 이벤트가 발생하면 `processing-service`가 이벤트를 처리하고, 그 결과를 `account-service`에 전달합니다.

### 5.1 호출 API

```text
POST /internal/v1/users/point-changed
```

요청에는 다음 정보가 포함됩니다.

| 필드 | 설명 |
| --- | --- |
| `eventId` | 이벤트를 구분하는 ID |
| `userId` | 포인트를 반영할 사용자 ID |
| `orderId` | 관련 주문 ID |
| `pointType` | 포인트 변경 유형 |
| `changeAmount` | 변경된 포인트 양 |
| `balanceAfter` | 변경 이후 최종 잔액 |
| `occurredAt` | 이벤트 발생 시각 |

### 5.2 처리 흐름

```text
1. processing-service가 포인트 반영 요청
2. 필수값 확인
3. 사용자 조회
4. 사용자 row 잠금
5. pointBalance를 balanceAfter 값으로 변경
6. 사용자 상세 캐시 삭제
7. 성공 응답
```

여기서 중요한 점은 `changeAmount`를 더하거나 빼서 잔액을 계산하지 않는다는 것입니다.

`account-service`는 전달받은 `balanceAfter`를 최종 잔액으로 저장합니다. 중복 처리 여부와 포인트 이력 관리는 `processing-service`에서 담당합니다.

## 6. 캐시 처리 방식

사용자 상세 조회는 Redis 캐시를 사용합니다.

| 상황 | 처리 |
| --- | --- |
| 사용자 상세 조회 | 캐시 우선 조회 |
| 캐시 없음 | DB 조회 후 캐시 저장 |
| 사용자 수정 | DB 반영 후 캐시 삭제 |
| 사용자 삭제 | DB 반영 후 캐시 삭제 |
| 포인트 잔액 반영 | DB 반영 후 캐시 삭제 |

캐시 삭제는 최신 정보가 다음 조회에서 다시 저장되도록 하기 위한 처리입니다.

## 7. API 요약

### 사용자 API

| Method | Endpoint | 설명 |
| --- | --- | --- |
| `GET` | `/api/v1/users/{userId}` | 사용자 상세 조회 |
| `GET` | `/api/v1/users` | 사용자 목록 조회 |
| `POST` | `/api/v1/users` | 사용자 생성 |
| `PUT` | `/api/v1/users/{userId}` | 사용자 수정 |
| `DELETE` | `/api/v1/users/{userId}` | 사용자 삭제 |

### 상품 API

| Method | Endpoint | 설명 |
| --- | --- | --- |
| `GET` | `/api/v1/products/{productId}` | 상품 상세 조회 |
| `PUT` | `/api/v1/products/{productId}` | 상품 수정 |

### 내부 API

| Method | Endpoint | 설명 |
| --- | --- | --- |
| `POST` | `/internal/v1/users/point-changed` | 사용자 포인트 잔액 반영 |

## 8. 주요 예외 상황

| 상황 | 처리 |
| --- | --- |
| 사용자를 찾을 수 없음 | 요청 실패 |
| 상품을 찾을 수 없음 | 요청 실패 |
| 이미 사용 중인 `loginId` | 사용자 생성 실패 |
| 이미 사용 중인 `email` | 사용자 생성/수정 실패 |
| 이미 사용 중인 `productCode` | 상품 수정 실패 |
| 포인트 반영 요청 필수값 누락 | 요청 실패 |
| 잘못된 사용자 상태값 | 요청 실패 |

## 9. 정리

`account-service`는 사용자와 상품의 기준 데이터를 관리합니다.

포인트 처리에서는 복잡한 이벤트 처리나 이력 관리를 직접 하지 않고, `processing-service`가 계산한 최종 잔액을 사용자 정보에 반영하는 역할만 담당합니다. 따라서 이 서비스의 핵심은 사용자 정보의 정확한 저장, 중복 검증, 최신 캐시 유지입니다.
